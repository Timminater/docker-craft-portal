# Portal languages

Craft Portal supports English and Dutch. It selects Dutch when the browser's preferred language list includes Dutch before another supported language; otherwise it uses English. Unsupported languages fall back to English. The document language, navigation, first-run setup, authentication, administration, dialogs and application-session bridge use the selected language. Dates and numbers use that language's browser formatting.

The language is a browser preference, not an account setting. Change your browser's preferred languages and reload the portal to change it. No extra environment variable or external translation service is required.

Application names, release versions, file names, user content and technical diagnostics from upstream releases remain as supplied. The language inside a launched ArtCraft application is controlled by that application.

## Validation

Run the ordinary test suite and JavaScript syntax checks first. Browser checks use real local HTTP servers and synthetic releases without production credentials:

```sh
CRAFT_BROWSER_TESTS=1 python -m pytest tests/browser -q
```

`test_i18n_browser.py` covers English, Dutch and an unsupported browser language, onboarding, login, applications, administration, users, activity, downloads, version dialogs and the launch bridge. It checks document language, localized date formatting, desktop/mobile overflow, compact collection headers, ready/pending application actions and browser console errors. Existing browser tests still cover authenticated WASM hosting, focus handling, rollback and user-origin isolation.

Set `CRAFT_SCREENSHOT_DIR` to save application-page desktop and mobile screenshots for visual review. Firefox tests require a locally installed Playwright Firefox browser; missing browsers are skipped unless `CRAFT_REQUIRE_BROWSERS=1` is set.

Translations live in `portal/static/i18n.js`. Use `CraftI18n.t(key, values)` for visible text and accessible labels; use count-based entries for plural forms. Missing Dutch entries fall back to their English entry, and unknown keys remain visible for diagnosis. Keep release diagnostics available rather than hiding them behind a generic translated message. When adding strings, add entries for both languages and extend `tests/test_i18n.py` or browser coverage where behavior changes.

The clean-console browser workflow records JavaScript exceptions, console errors, failed requests and HTTP error responses per page without suppression. The separate invalid-login test deliberately expects one unauthorized response to validate localized authentication feedback. Optional screenshot output also includes a JSON console report listing the exercised pages.
